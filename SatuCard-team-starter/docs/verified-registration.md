# Подтверждённая регистрация и собственный профиль

## Поведение

- Вход по паролю работает только с существующим аккаунтом. Регистрация по email требует подтверждения письмом и не сохраняет сессию из ответа signup.
- Google подтверждает владение почтой. OAuth-провайдер Supabase может автоматически создать техническую запись пользователя при первом входе. Это ещё не завершённый профиль SatuCard: пользователь обязан самостоятельно ввести имя и фамилию на `profile.html`.
- Ни имя из Google, ни первая часть email не считаются заполненным профилем. Имя в шапке берётся из сохранённого профиля. Изменение доступно в кабинете.
- Вход по коду отправляет запрос с `create_user: false`: кнопка входа не регистрирует новый email.
- Только `/api/profile` может менять поля профиля. ID и email берутся из проверенного сервером пользователя; клиент не может менять поля доступа.
- API публикации и коллекции требуют подтверждённую почту и завершённый профиль. Открытый редактор и скачивание доступны гостю.

## Старые учебные аккаунты

Ранее email подтверждался автоматически, поэтому старый пароль не доказывает владение ящиком. Миграция помечает существующие профили `mail_proof_required = true`. Для каждого такого сеанса требуется реальный OAuth-вход или одноразовая ссылка/код из почты. Наличие когда-либо привязанного Google и редактируемое поле `email_verified` в metadata не дают права обхода.

Флаг не снимается при заполнении профиля или входе владельца через Google: старый чужой пароль не должен снова заработать. У новых профилей флаг по умолчанию false; обязательное подтверждение в Supabase защищает их регистрацию по email. Пользователи, ID, публикации и изображения при миграции не удаляются.

Проверку делает сервер после валидации bearer-токена в Supabase. Дополнительные restrictive RLS-политики защищают прямое чтение profiles/cards с этим токеном. Функция `satucard_token_guard` в Custom Access Token hook не позволяет старому паролю получить либо обновить токен Auth в обход сайта. Публичные опубликованные карточки остаются публичными.

## Развёртывание

1. В Supabase включить **Confirm email** и настроить SMTP. Основной пароль Google для SMTP не используется. Пароль приложения вводит владелец в Supabase; в репозитории секретов нет.
2. Выполнить `database/verified-registration.sql`, затем `database/legacy-token-guard.sql` в SQL Editor до публикации кода. Подключить `public.satucard_token_guard` в Authentication → Auth Hooks → Custom Access Token. Для новой установки сначала выполнить `database/schema.sql`, затем эти миграции. Старые password-сеансы при переходе следует завершить: их владельцы войдут через Google или почтовый код.
3. В URL Configuration установить Site URL `https://satucard-team.vercel.app/auth.html`. Оставить точные разрешённые callback-адреса.
4. Настроить письмо подтверждения и письмо входа: показывать `{{ .Token }}` и ссылку на `{{ .SiteURL }}?token_hash={{ .TokenHash }}&type=signup` либо `type=email` соответственно. Приложение очищает адрес до проверки одноразового токена у Supabase. Произвольный fragment с access_token не принимается.
5. Разместить код через GitHub/Vercel. Проверить Google, незавершённый профиль, неверный код, фактическую доставку письма, подтверждение email и повторный вход.

Gmail SMTP пригоден для небольшой учебной нагрузки; Supabase предупреждает о возможной проблеме доставляемости личной почты. Для коммерческого запуска нужен сервис транзакционных писем с подтверждённым доменом. Лимиты отправки не отключать.

## Проверки

`node --test tests/*.test.js` проверяет серверный запрет неподтверждённого email, старой password-сессии и незавершённого профиля, изоляцию владельца, валидацию имени, OTP без автосоздания, очистку ссылок и PKCE.
